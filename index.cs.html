Vizuální průvodce

Git srozumitelně.

Praktický vizuální úvod do správy verzí: od prvního commitu až po jistou spolupráci a bezpečnou obnovu změn.

Začněte zde

Jeden nástroj. Tři užitečné pohledy.

Git zaznamenává změny do historie, kterou můžete prohlížet, sdílet, větvit a obnovovat.

Projektové řízení · Zviditelněte změny

Propojte práci s rozhodnutími, kontrolami, vydáními a dohledatelnou historií projektu. Příkazy nejsou nutné.

Architektura · Navrhněte tok práce

Zvolte pravidla pro repozitáře a větve, která vyvažují rychlost integrace, potřeby vydávání a správu.

Vývoj · Získejte jistotu

Ve cvičném repozitáři si bezpečně vyzkoušejte prohlížení změn, jejich přípravu, vytváření commitů, synchronizaci, řešení konfliktů a obnovu.

Cíle kurzu: vysvětlit distribuovanou správu verzí, orientovat se v datovém modelu Gitu, používat běžné příkazy a zvolit týmový postup s ohledem na jeho kompromisy.

Modul 1 · Co je Git?

Správa verzí dává změnám jasnou podobu.

Bez správy verzí si týmy předávají soubory a doufají, že jejich názvy vysvětlí historii. Git uchovává trvalou a přehlednou historii snímků projektu.

Uchovávejte historii

Zjistěte, jak a kdy se soubor změnil a kdo změnu zaznamenal.

Spolupracujte

Pracujte souběžně, kontrolujte navržené změny a pak je spojte.

Obnovujte

Porovnávejte verze a v případě potřeby se vraťte ke známému funkčnímu stavu.

Historii Gitu chápejte jako posloupnost pojmenovaných a kontrolovatelných bodů — nikoli jako zálohovací disk nebo jeho náhradu.

Modul 1 · Dva modely

Git je distribuovaný: každý klon obsahuje repozitář.

Centralizovaný model · SVN, CVS

Klienti získávají pracovní soubory z centrálního serveru. Server je hlavním zdrojem historie; k zaznamenání sdílených změn je obvykle potřeba připojení k síti.

Distribuovaný model · Git

Každý klon obsahuje lokální repozitář a historii projektu. Pracovat, vytvářet commity i provádět řadu kontrol lze bez připojení; sdílení probíhá výměnou commitů.

Modul 4 · Od úpravy ke spolupráci

Podívejte se, kam jednotlivé příkazy Gitu přesouvají změny.

Lokální změny se stanou commity, které se pak přesouvají mezi vaším repozitářem a sdíleným vzdáleným repozitářem.

Tok změn: git add připraví změny; git commit je uloží lokálně; git push sdílí commity. git fetch stahuje bez začlenění; git pull stahuje a začleňuje.

Modul 1 · Co Git je — a co není

Git uchovává historii. Platformy pomáhají týmům ji využívat.

Git nabízí

  • Lokální historii a větvení
  • Kontrolu integrity obsahu pomocí hashů objektů
  • Nástroje pro porovnávání, slučování a sdílení práce

GitHub, GitLab, Azure DevOps a Bitbucket nabízejí

  • Hostované repozitáře a řízení přístupu
  • Požadavky na začlenění změn (pull/merge requests), kontroly a evidenci úkolů
  • Automatizaci, vydávání verzí a funkce pro týmovou spolupráci

Integrita: Git identifikuje objekty pomocí hashů odvozených z obsahu (algoritmus závisí na formátu repozitáře). Linus Torvalds vytvořil Git v roce 2005 pro vývoj jádra Linuxu; distribuovaný návrh a levné větvení podporují souběžnou spolupráci.

Modul 3 · Začínáme

Nastavte svou identitu a pak vytvořte nebo naklonujte repozitář.

Nainstalujte Git pomocí správce balíčků svého operačního systému nebo z oficiální stránky Git. Ověřte nainstalovanou verzi a nastavte jméno a e-mail, které se budou zobrazovat u vašich commitů.

git --version
git config --global user.name "Ada Lovelace"
git config --global user.email "ada@example.com"

Nahraďte ukázkové jméno a e-mail. Použijte e-mail vhodný pro pracovní účet. Parametr --global nastaví výchozí hodnoty pro tohoto uživatele; vynechte jej, chcete-li nastavit pouze aktuální repozitář. Nastavení ověřte příkazem git config --list --show-origin.

Vytvoření prázdného repozitáře

mkdir demo
cd demo
git init

Naklonování existujícího repozitáře

git clone <repository-url>
cd <repository-name>

Zástupné hodnoty v ostrých závorkách, například <repository-url> (adresa repozitáře), nahraďte vlastními údaji bez závorek. Názvy příkazů a přepínačů se nepřekládají.

Přihlašovací údaje jsou oddělené od identity autora commitůModul 3
Modul 3 · Nastavení repozitáře

Mějte pod kontrolou generované soubory, rozdíly mezi platformami i přihlašovací údaje.

.gitignore

Uvádí nesledované cesty, které má Git ignorovat, například výstupy sestavení a lokální tajné údaje. Již commitované soubory tím nepřestanou být sledovány.

.gitattributes

Umožňuje sjednotit normalizaci textu, chování diffu a práci s binárními soubory napříč přispěvateli. Záleží-li na koncích řádků, stanovte v projektu výslovná pravidla.

Ověřování

Používejte schváleného správce přihlašovacích údajů pro HTTPS nebo nastavte klíč SSH. Nikdy nevkládejte tokeny ani soukromé klíče do repozitáře.

Dostal se tajný údaj do commitu? Odstranění souboru v pozdějším commitu jej z historie nevymaže. Nejprve přihlašovací údaj zneplatněte nebo obměňte; potom koordinujte vyčištění historie a informování dotčených osob.

Modul 4 · Každodenní příkazy

Nejprve změny zkontrolujte. Potom vyberte, co zaznamenat.

git status · kontrola stavu

Účel: shrne aktuální větev, připravené a nepřipravené změny i nesledované soubory.

Syntaxe: git status [--short]

Příklad: nepřipravenou úpravu zobrazí v části „Changes not staged for commit“ jako modified: README.md. Parametr --short zobrazí stručný výpis.

Úskalí: příkaz stav shrnuje, ale nezobrazuje vlastní rozdíl.

git diff · kontrola obsahu

Účel: porovná pracovní strom s indexem; připravené změny porovnáte s HEAD pomocí --staged.

Syntaxe: git diff [--staged]

Příklad: git diff --staged zobrazí změny připravené pro příští commit.

Přepínače: --stat zobrazí souhrn; --word-diff porovnává jednotlivá slova.

Úskalí: samotný git diff připravené změny nezahrnuje.

Pracovní stromnepřipravené úpravy
git diff →
Indexpřipravený snímek
--staged →
HEADposlední commit

git status shrnuje oba stavy; git diff zobrazí podrobnosti rozdílů.

$ git status --short
 M README.md
$ git diff --stat
 README.md | 2 ++
 1 file changed, 2 insertions(+)

Ukázkový výstup: status používá dva sloupce pro stav indexu a pracovního stromu; mezera následovaná znakem M označuje nepřipravenou změnu.

Výstupy Gitu jsou v příkladech ponechány v angličtině; jazyk výpisů závisí na instalaci.

Postup · před změnou stavu nejprve zkontrolujte změnyModul 4
Modul 4 · Příprava změn

git add vybírá obsah příštího commitu.

Účel a syntaxe

Přidá vybraný obsah souborů z pracovního stromu do indexu.

git add README.md
git add src/
git add -p

-p interaktivně vybírá části změn. git add -A připraví všechna přidání, úpravy i odstranění v repozitáři.

Příklad a úskalí

Upravte dva soubory, jeden připravte a zkontrolujte výsledek:

git add README.md
git status
git diff --staged

Do příštího commitu se dostane pouze připravený obsah. Opětovná příprava souboru aktualizuje jeho připravený snímek. Před použitím -A zkontrolujte, zda omylem nepřidáváte nežádoucí soubory.

Dobrý návyk: před commitem zkontrolujte git diff --staged. Index je užitečné místo pro kontrolu, nikoli zbytečná práce.

$ git add README.md
(při úspěchu bez výstupu)
$ git status --short
M  README.md

Modul 4 · Commit

Commit je pojmenovaný kontrolní bod s popisem.

Účel a syntaxe

Zaznamená připravený snímek do lokální historie.

git commit -m "Zdokumentovat postup nastavení"

-m zadá popis přímo v příkazu; bez něj Git otevře nastavený textový editor.

Příklad a úskalí

Předem: připravte zamýšlené soubory. Poté: nový commit se stane nejnovějším commitem aktuální větve.

Napište stručný popis záměru změny, například v infinitivu. Vysvětlete, proč je změna důležitá. Vyhněte se vágním popisům jako „aktualizace“ nebo „oprava“.

Úskalí: Git ve výchozím nastavení odmítne commit beze změn. Commit zůstává lokální, dokud jej neodešlete.

$ git commit -m "Zdokumentovat postup nastavení"
[main 8c14f2a] Zdokumentovat postup nastavení
 1 file changed, 3 insertions(+)

Ukázkový výstup: ID commitů a počet souborů se liší. Název větve v hranatých závorkách a krátký hash označují nový lokální commit.

Indexzkontrolované změny
git commit →
Lokální historienový commit

Commit zaznamenává pouze připravený obsah, nikoli všechny upravené soubory.

Modul 4 · Prohlížení historie

Historie odpovídá na otázky „co se změnilo?“ a „proč?“

git log · procházení commitů

Účel: zobrazí historii commitů.

Syntaxe: git log [--oneline --graph --decorate]

Příklad: git log --oneline --graph zobrazí stručný graf.

Úskalí: historie standardně sleduje aktuální větev, pokud ji přepínače nebo reference nerozšíří.

git show · kontrola jednoho commitu

Účel: zobrazí metadata commitu a jeho změny.

Syntaxe: git show <commit>

Příklad: git show HEAD zkontroluje nejnovější commit aktuální větve.

Přepínače: --stat zobrazí souhrn. Cíl lze určit ID commitu nebo značkou tag.

Úskalí: rozsáhlé změny se mohou zobrazit v prohlížeči výpisu; klávesou q jej ukončíte.

$ git log --oneline -1
8c14f2a Zdokumentovat postup nastavení

Ukázkový výstup z předchozího příkladu. Konkrétní hash a popis závisí na vašem repozitáři.

Jak kontrolovat: nejprve projděte popis a souhrn; přesný obsah zjistíte přečtením změn.

$ git show --stat --oneline HEAD
8c14f2a Zdokumentovat postup nastavení
 README.md | 3 +++
 1 file changed, 3 insertions(+)

Modul 4 · Sdílení a příjem commitů

Fetch stáhne. Pull stáhne a začlení. Push odešle.

git remote · správa vzdálených repozitářů

Účel: vypíše nebo spravuje názvy a adresy URL vzdálených repozitářů.

Syntaxe: git remote -v; git remote add <name> <url>.

Příklad: origin je obvyklý název vzdáleného repozitáře, ze kterého byl klon vytvořen.

Úskalí: pojmenovaný remote je nastavení připojení, nikoli druhý pracovní adresář.

git fetch · stažení referencí

Účel: stáhne vzdálené commity a aktualizuje sledovací reference, aniž by je začlenil do aktuální větve.

Syntaxe: git fetch <remote>

Příklad: proveďte fetch a potom porovnejte historii příkazem git log HEAD..origin/main.

Úskalí: samotný fetch neaktualizuje právě načtené soubory.

git pull · stažení a začlenění

Účel: stáhne změny z určené nebo sledované vzdálené větve a začlení je do aktuální větve pomocí merge nebo rebase podle přepínačů a nastavení.

Syntaxe: git pull [--rebase] <remote> <branch>

Příklad: git pull --rebase origin main.

Úskalí: zjistěte, zda tým používá merge, nebo rebase; případné konflikty vyřešte.

git push · zveřejnění commitů

Účel: odešle lokální commity do vzdálené větve.

Syntaxe: git push -u <remote> <branch>

Příklad: git push -u origin feature/docs nastaví sledování nadřazené větve.

Úskalí: push může být odmítnut, pokud se vzdálená historie posunula; místo přepsání práce kolegů změny stáhněte a začleňte.

Lokální větevvaše commity
push →
Vzdálený repozitářsdílené commity
← fetch
Sledovací referencenapříklad origin/main

Pull po stažení přidává krok začlenění; nejde pouze o stažení souborů.

$ git remote -v
origin  https://example.com/team/project.git (fetch)
origin  https://example.com/team/project.git (push)
$ git fetch origin
From https://example.com/team/project
   a13f1c0..b02a7d1  main -> origin/main
$ git push -u origin feature/docs
To https://example.com/team/project.git
 * [new branch]      feature/docs -> feature/docs
branch 'feature/docs' set up to track 'origin/feature/docs'.

Ukázková adresa vzdáleného repozitáře a ID objektů jsou zástupné hodnoty. Úspěšný fetch aktualizuje sledovací reference, nikoli pracovní strom.

Pokud pull nepřinese žádné nové commity, Git může oznámit Already up to date.; při začlenění rychlým posunem se větev posune bez vytvoření merge commitu.

Modul 4 · Souběžná práce

Větvením oddělte práci; příkazem merge ji začleňte.

git branch · výpis nebo vytvoření

Syntaxe: git branch [--all]; git branch <name>. Pomocí -d odstraníte sloučenou lokální větev.

Úskalí: vytvořením větve se na ni nepřepnete. Nesloučenou práci nemažte bez rozmyslu.

git switch · přepnutí mezi větvemi

Syntaxe: git switch <name>; git switch -c <new-name>.

Příklad: git switch -c feature/search.

Úskalí: Git může přepnutí zablokovat, pokud by se tím přepsaly lokální úpravy.

git merge · začlenění historie

Syntaxe: git merge <branch>.

Při rychlém posunu (fast-forward) se pouze posune ukazatel aktuální větve. Při sloučení rozvětvené historie vznikne merge commit se dvěma rodičovskými commity.

Úskalí: konflikty vyžadují úpravu souborů, přípravu vyřešených souborů a dokončení merge commitu.

git rebase · přehrání commitů

Syntaxe: git rebase <base>.

Znovu přehraje vaše commity nad novým základem a vytvoří lineární posloupnost s novými ID commitů.

Zlaté pravidlo: nerebasujte historii, na které už mohou být založeny změny ostatních.

$ git branch --list
* main
$ git switch -c feature/search
Switched to a new branch 'feature/search'
$ git rebase main
Current branch feature/search is up to date.
$ git switch main
Switched to branch 'main'
$ git merge feature/search
Already up to date.

V tomto příkladu zatím nevznikl nový commit, takže rebase ani merge nemají co začlenit. Praktické cvičení ukazuje rychlý posun po vytvoření nového commitu.

Před přepisováním nebo vynuceným odesláním sdílené historie se zastavteModul 4
Modul 4 · Odložení práce a označení verzí

Dočasné úpravy odložte pomocí stash. Důležité milníky označte tagem.

git stash · odložení rozpracované práce

Syntaxe: git stash push -m "popis"; git stash list; git stash pop.

Příklad: odložte úpravy, abyste mohli změnit kontext práce, a později je znovu použijte.

Přepínače: -u zahrne nesledované soubory. apply ponechá záznam stash; pop jej po úspěšném použití odstraní.

Úskalí: záznamy stash jsou lokální a snadno se na ně zapomene; trvalou práci raději commitněte.

git tag · označení commitu vydání

Syntaxe: git tag -a v1.2.0 -m "Vydání 1.2.0"; seznam zobrazí git tag.

Účel: anotované tagy zaznamenávají pojmenovaný milník včetně metadat.

Zveřejnění: git push origin v1.2.0 (nebo git push --tags pro všechny tagy).

Úskalí: běžné odeslání větví tagy automaticky neodešle; dohodněte si pravidla verzování.

$ git stash list
stash@{0}: On main: Rozpracováno: upravit popisky mapy
$ git tag
v1.2.0

Modul 5 · Konflikt je rozhodnutí, nikoli selhání

Konflikt znamená, že Git potřebuje člověka, který určí výslednou podobu změn.

Konflikty obvykle vznikají, když se v obou historiích mění překrývající se řádky nebo když jedna změna přejmenuje či odstraní soubor, který druhá upravuje. Git integraci pozastaví, aby člověk mohl vytvořit zamýšlený výsledek.

Postup řešení pro vývojáře

  1. Pomocí git status zjistěte, které soubory mají konflikt.
  2. Otevřete každý soubor, porovnejte obě strany a upravte výsledný obsah podle záměru.
  3. Odstraňte značky konfliktu, spusťte příslušné testy a připravte vyřešené soubory.
  4. Dokončete merge nebo rebase podle pokynů Gitu.

Značky konfliktu

<<<<<<< HEAD
verze aktuální větve
=======
příchozí verze
>>>>>>> other-branch

Značky slouží pouze jako pomůcka, do výsledného obsahu nepatří. Některé nástroje nabízejí vizuální editor pro porovnání obou stran.

Nevybírejte naslepo možnost „ours“ nebo „theirs“ pro každý konflikt. Ověřte správné chování s autory změn a zkontrolujte společný výsledek.

Modul 6 · Architektura a správa

Volba mezi monorepozitářem a více repozitáři závisí na vlastnictví a nástrojích.

Jeden repozitář (monorepo)

Výhody: atomické změny napříč projekty, sdílené nástroje a snadno dohledatelný kód.

Náklady: škálování CI a oprávnění, pravidla pro celý repozitář a rozsáhlá historie při klonování.

Více repozitářů (multi-repo)

Výhody: nezávislé vlastnictví, řízení přístupu a četnost vydávání.

Náklady: koordinace změn napříč repozitáři, duplicitní nástroje a správa verzí závislostí.

Chraňte větve

Podle potřeby vyžadujte kontrolu změn, úspěšné testy a omezte přímé odesílání.

Vyjasněte vlastnictví

Pro kritické komponenty používejte CODEOWNERS nebo obdobné směrování kontrol.

Automatizujte dohledatelnost

Jednotnými pravidly propojte změny s evidovanými úkoly, sestaveními, artefakty a vydáními.

Conventional Commits

Modul 8 · Osvědčené postupy

Vytvářejte historii užitečnou pro dalšího člověka.

Commitujte často

Malé, samostatné změny se snáze vysvětlují, kontrolují, testují i vracejí.

Pište výstižné popisy

Popište záměr a dopad, nejen technické provedení.

Před sdílením kontrolujte

Zkontrolujte připravené rozdíly, stav, testy a generované soubory.

Začleňujte včas

Krátké cykly zpětné vazby omezují rozcházení větví a nečekané konflikty.

Chraňte přihlašovací údaje

Používejte skenování tajných údajů a schválené úložiště; tajné údaje nikdy necommitujte.

Dokumentujte postup

Zpřístupněte pravidla pro vydávání, kontrolu, vlastnictví a obnovu.

Dobrá historie je nástrojem spolupráceModul 8
Modul 8 · Chraňte to, co sdílíte

Prevence je jednodušší než čištění zveřejněné historie.

Nikdy necommitujte tajné údaje

Ukládejte přihlašovací údaje ve schválených správcích tajných údajů. Pokud uniknou, ihned je zneplatněte nebo obměňte — i když commit později odstraníte.

Zapněte skenování tajných údajů na platformě a zkontrolujte přístupy k dotčeným systémům.

S velkými soubory zacházejte uvážlivě

Git ukládá snímky; časté změny velkých binárních souborů mohou zvětšit historii repozitáře. Git LFS uchovává v Gitu ukazatele a obsah souborů v odděleném úložišti.

Před zavedením LFS ověřte kvóty, dobu uchovávání, přístupy a pravidla zálohování.

Zabezpečte postup

Minimální oprávnění, chráněné větve, povinná kontrola a podepsané commity či tagy posilují důvěryhodnost původu.

Nevhodným postupům se vyhněte

Rozsáhlým nesouvisejícím commitům, vynucenému odesílání do sdílených větví, dlouho neintegrovaným větvím a bezmyšlenkovitému commitování generovaných výstupů.

Odstranění souboru s tajným údajem v pozdějším commitu nevymaže starší kopie z historie ani klonů. Nejprve údaj obměňte; poté postupujte podle pravidel pro incidenty a čištění repozitáře.

Příručka · Časté dotazy a další četba

Běžné otázky a stručné odpovědi.

Je Git zálohovací nástroj?

Sám o sobě ne. Lokální repozitář je pouze jedna kopie; důležitou práci zálohujte a hostujte podle schválených pravidel.

Odesílá se každý commit na GitHub?

Ne. Commity zůstávají lokální, dokud je neodešlete do vzdáleného repozitáře. Lokální commity můžete vytvářet a kontrolovat i bez připojení.

Měli bychom vždy používat rebase?

Ne. Dodržujte týmovou konvenci. Rebase může vytvořit lineární historii, ale mění ID commitů; sdílenou historii nepřepisujte.

Proč vznikne konflikt při slučování?

Git nedokáže určit zamýšlený výsledek překrývajících se úprav nebo neslučitelných operací se soubory. Člověk musí výslednou změnu vyřešit a ověřit.

Lze obnovit odstraněnou větev?

Často ano, pokud je její commit stále dostupný v lokálním reflogu. Nejprve jej zkontrolujte a pak vytvořte záchrannou větev. Záznamy reflogu jsou lokální a časem expirují.
