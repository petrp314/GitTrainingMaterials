Module 1 · What is Git? [All]

Version control makes change legible.

Without version control, teams trade files and hope filenames tell the story. Git keeps a durable, inspectable history of project snapshots.

Remember

See how and when a file changed, and who recorded the change.

Collaborate

Work in parallel, review proposed changes, then combine them.

Recover

Compare versions and return to a known-good state when needed.

Think of Git history as a sequence of named, reviewable checkpoints—not a backup drive or a substitute for one.

Module 1 · Two models [All]

Git is distributed: every clone has a repository.

Centralized model · SVN, CVS

Clients check out working files from a central server. The server is the main source of history; network access is commonly needed to commit shared changes.

Distributed model · Git

Each clone has a local repository and project history. Work, commits, and many inspections can happen offline; sharing happens by exchanging commits.

Central serverauthoritative history
↔
Working copyclient
···
Git clone Arepo + files
↔
Git clone Brepo + files

The hosting service is a convenient shared endpoint; Git itself is the version-control system.

Module 1 · What Git is—and isn't [All]

Git stores history. Platforms help teams use it.

Git provides

  • Local history and branching
  • Content integrity checked with object hashes
  • Tools to compare, combine, and share work

GitHub, GitLab, Azure DevOps, Bitbucket provide

  • Hosted repositories and access controls
  • Pull/merge requests, reviews, and issue workflows
  • Automation, releases, and team collaboration features

Integrity: Git identifies objects by SHA-based content hashes (the hash algorithm depends on repository format). Linus Torvalds created Git in 2005 to support Linux kernel development; its distributed design and inexpensive branches fit parallel contributions.

Module 3 · Get started [Dev] [All]

Set your identity, then create or copy a repository.

Install Git from your operating system's package manager or the official Git downloads. Verify the installed version, then set the name and email that will appear on your commits.

git --version
git config --global user.name "Ada Lovelace"
git config --global user.email "ada@example.com"

Replace the sample name and email. Use the email address appropriate for your work account. --global sets your default for this user; omit it to configure just the current repository. Check settings with git config --list --show-origin.

Create an empty repository

mkdir demo && cd demo
git init

Copy an existing repository

git clone <repository-url>
cd <repository-name>

Module 3 · Repository setup [Dev] [Architect]

Keep generated files, platform differences, and credentials intentional.

.gitignore

Lists untracked paths Git should ignore, such as build output and local secrets. It does not untrack files already committed.

.gitattributes

Can standardize text normalization, diff behavior, and binary handling across contributors. Prefer explicit project rules where line endings matter.

Authentication

Use an approved credential manager with HTTPS or configure an SSH key. Never paste tokens or private keys into a repository.

Secret already committed? Removing the file in a later commit does not erase it from history. Revoke/rotate the credential first; then coordinate history cleanup and notification.

Module 4 · Everyday commands [Dev] [All]

First inspect. Then select what to record.

git status · inspect state

Purpose: summarize current branch and staged, unstaged, and untracked changes.

Syntax: git status [--short]

Example: reports modified: README.md as unstaged. --short is compact.

Pitfall: it summarizes; it does not show the actual diff.

git diff · inspect content

Purpose: compare working-tree changes; staged changes need a separate flag.

Syntax: git diff [--staged]

Example: git diff --staged shows exactly what the next commit would contain.

Options: --stat summarizes; --word-diff compares words.

Pitfall: plain git diff omits staged changes.

Working treeunstaged edits
git diff →
Indexstaged snapshot
--staged →
HEADlast commit

git status summarizes both comparisons; git diff shows their details.

$ git status --short
 M README.md
$ git diff --stat
 README.md | 2 ++
 1 file changed, 2 insertions(+)

Illustrative output: status uses two columns for index and working-tree state; a leading space then M means unstaged modification.

Command pattern · inspect before changing stateModule 4
Module 4 · Stage changes [Dev]

git add chooses content for the next commit.

Purpose and syntax

Add selected file contents from the working tree to the index.

git add README.md
git add src/
git add -p

-p interactively selects change hunks. git add -A stages all additions, modifications, and deletions in the repository.

Example and pitfalls

Edit two files, stage one, then inspect:

git add README.md
git status
git diff --staged

Only staged content goes into the next commit. Staging a file again updates its staged snapshot. Check for accidental files before using -A.

Habit: review git diff --staged before committing. The index is a useful review boundary, not busywork.

$ git add README.md
(no output on success)
$ git status --short
M  README.md
State change · working tree → indexModule 4
Module 4 · Commit [Dev] [All]

A commit is a named checkpoint with a message.

Purpose and syntax

Record the staged snapshot in local history.

git commit -m "Document setup steps"

-m supplies a one-line message; without it, Git opens the configured editor.

Example and pitfalls

Before: stage intended files. After: the new commit becomes the current branch tip.

Write a short imperative summary of why the change matters. Avoid vague messages such as “updates” or “fix”.

Pitfall: an empty commit may be rejected by default. A commit is local until pushed.

$ git commit -m "Document setup steps"
[main 8c14f2a] Document setup steps
 1 file changed, 3 insertions(+)

Illustrative output: commit IDs and file counts vary. The bracketed branch and short hash identify the new local commit.

Indexreviewed changes
git commit →
Local historynew commit

A commit records only staged content, not every modified file.

Good commits are small enough to understand and useful enough to reviewModule 4
Module 4 · Inspect history [Dev] [All]

History answers “what changed?” and “why?”

git log · browse commits

Purpose: view commit history.

Syntax: git log [--oneline --graph --decorate]

Example: git log --oneline --graph gives a compact graph.

Pitfall: history follows the current branch unless options or refs broaden it.

git show · inspect one commit

Purpose: show a commit's metadata and patch.

Syntax: git show <commit>

Example: git show HEAD inspects the current tip.

Options: --stat shows a summary. A commit ID or tag can identify a target.

Pitfall: large patches can use a pager; press q to leave it.

$ git log --oneline -1
8c14f2a Document setup steps

Illustrative output from the prior example. The exact hash and message depend on your repository.

Review lens: scan the message and summary first; read the patch when you need the exact content.

$ git show --stat --oneline HEAD
8c14f2a Document setup steps
 README.md | 3 +++
 1 file changed, 3 insertions(+)
Local history is available without a network connectionModule 4
Module 4 · Share and receive commits [Dev] [All]

Fetch previews. Pull integrates. Push publishes.

git remote · name a repository

Purpose: list or manage remote names and URLs.

Syntax: git remote -v; git remote add <name> <url>.

Example: origin is the conventional clone remote.

Pitfall: a remote is configuration, not a second working directory.

git fetch · download references

Purpose: get remote commits and update remote-tracking refs without integrating them into your current branch.

Syntax: git fetch <remote>

Example: fetch, then compare with git log HEAD..origin/main.

Pitfall: fetching alone does not update checked-out files.

git pull · fetch + integrate

Purpose: fetch, then integrate the upstream branch by merge or configured rebase.

Syntax: git pull [--rebase] <remote> <branch>

Example: git pull --rebase origin main.

Pitfall: know whether your team expects merge or rebase; resolve conflicts if they arise.

git push · publish commits

Purpose: send local commits to a remote branch.

Syntax: git push -u <remote> <branch>

Example: git push -u origin feature/docs sets upstream tracking.

Pitfall: push can be rejected if remote history has advanced; fetch and integrate instead of overwriting teammates' work.

Local branchyour commits
push →
Remoteshared commits
← fetch
Remote-tracking refwhat was fetched

Pull adds an integration step after fetch; it is not merely a download.

$ git remote -v
origin  https://example.com/team/project.git (fetch)
origin  https://example.com/team/project.git (push)
$ git fetch origin
From https://example.com/team/project
   a13f1c0..b02a7d1  main -> origin/main
$ git push -u origin feature/docs
To https://example.com/team/project.git
 * [new branch]      feature/docs -> feature/docs
branch 'feature/docs' set up to track 'origin/feature/docs'.

Example remote URL and object IDs are placeholders. A successful fetch updates remote-tracking references, not your working tree.

After a pull with no incoming commits, Git may report Already up to date.; if it integrates a fast-forward, the branch tip advances without a merge commit.

Prefer fetch when you want to inspect before integratingModule 4
Module 4 · Parallel work [Dev] [Architect]

Branch to isolate work; merge to integrate it.

git branch · list or create

Syntax: git branch [--all]; git branch <name>. Use -d to delete a merged local branch.

Pitfall: creating a branch does not switch to it. Do not delete unmerged work casually.

git switch · move between branches

Syntax: git switch <name>; git switch -c <new-name>.

Example: git switch -c feature/search.

Pitfall: Git may prevent switching if local edits would be overwritten.

git merge · integrate history

Syntax: git merge <branch>.

A fast-forward moves the branch pointer when possible; otherwise Git creates a merge commit with both histories as parents.

Pitfall: conflicts require editing, staging resolved files, then completing the merge commit.

git rebase · replay commits

Syntax: git rebase <base>.

Replays your commits on a new base to create a linear sequence with new commit IDs.

Golden rule: do not rebase history others may already have based work on.

$ git branch --list
* main
  feature/search
$ git switch -c feature/search
Switched to a new branch 'feature/search'
$ git merge feature/search
Updating 4a9d2b1..d20b81c
Fast-forward
$ git rebase main
Successfully rebased and updated refs/heads/feature/search.
Pause before rewriting or force-pushing shared historyModule 4
Module 4 · Shelve and label [Dev]

Stash temporary edits. Tag meaningful milestones.

git stash · shelve work in progress

Syntax: git stash push -m "message"; git stash list; git stash pop.

Example: stash edits to switch context, then apply them later.

Options: -u includes untracked files. apply keeps the stash; pop applies and removes it if successful.

Pitfall: stashes are local and easy to forget; commit durable work instead.

git tag · name a release commit

Syntax: git tag -a v1.2.0 -m "Release 1.2.0"; list with git tag.

Purpose: annotated tags record a named milestone with metadata.

Publish: git push origin v1.2.0 (or git push --tags for all tags).

Pitfall: tags are not automatically pushed with ordinary branch pushes; agree on version policy.

$ git stash list
stash@{0}: On main: WIP: adjust map labels
$ git tag
v1.2.0

Module 5 · Branching and merging [All]

Branches let teams work in parallel without duplicating a project.

A branch begins as a movable name at a commit. Git reuses shared history; the branch costs little and makes an isolated line of work easy to discuss.

↘

↗

Isolation helps organize work; it does not remove the need to integrate and test it.

Keep the branch focused

One feature or fix makes review and rollback easier.

Integrate regularly

Short-lived branches reduce the distance between parallel changes.

Automate checks

Run tests and validation before changes reach a shared branch.

Module 5 · Conflicts are a decision, not a failure [All]

A conflict means Git needs a human to choose the combined result.

Conflicts commonly occur when both histories change overlapping lines, or when one renames/deletes a file another changes. Git pauses integration so a person can create the intended result.

Developer resolution loop

  1. Read git status to identify conflicted files.
  2. Open each file; compare both sides and edit the final intended content.
  3. Remove conflict markers, run relevant tests, then stage resolved files.
  4. Complete the merge or rebase as Git instructs.

Conflict markers

<<<<<<< HEAD
current branch version
=======
incoming version
>>>>>>> other-branch

Markers are scaffolding, not valid final content. Some tools offer a visual side-by-side editor.

Do not blindly choose “ours” or “theirs” for every conflict. Confirm behavior with the change owners and validate the combined result.

Conflict resolution is collaboration encoded in a file editModule 5

Module 6 · Make trade-offs explicit [PM] [Architect]

Ask what must be true for the workflow to succeed.

Release cadence

Weekly releases may favor a lighter flow than several supported release lines.

Team size & ownership

Clear reviewers, component ownership, and merge responsibility matter as teams grow.

Feedback speed

Short branches depend on trustworthy tests and quick CI feedback.

Risk & compliance

Audit evidence, approvals, signed artifacts, and access controls may be mandatory.

Deployment strategy

Feature flags and backward-compatible changes help separate deployment from release.

Support obligations

Multiple maintained versions need an explicit patch and release policy.

Scenario: a 40-person team releases weekly. Start by testing short-lived reviewed branches or trunk-based development against CI speed, ownership boundaries, and release risk—not by adopting Gitflow by default.

Module 6 · Architecture and governance [Architect]

Monorepo or multi-repo is an ownership and tooling decision.

Monorepo

Benefits: atomic cross-project changes, shared tooling, discoverable code.

Costs: scaling CI and permissions, repository-wide conventions, large checkout history.

Multi-repo

Benefits: independent ownership, access control, and release cadence.

Costs: coordinated cross-repo changes, duplicated tooling, dependency version management.

Protect branches

Require reviews, passing checks, and restricted direct pushes where appropriate.

Clarify ownership

Use CODEOWNERS or equivalent review routing for critical components.

Automate traceability

Link changes to issues, builds, artifacts, and releases with a consistent policy.

Module 7 · Undo and recovery [Dev]

Choose an undo command by where the change lives.

SituationCommandEffect
Discard unstaged edits in a pathgit restore <path>Replaces working-tree file from the index. Discards those edits.
Unstage a file, keep editsgit restore --staged <path>Resets index entry to HEAD; working-tree edits remain.

Module 7 · Reset carefully [Dev]

git reset moves the current branch to a chosen commit.

ModeBranch / HEADIndexWorking treeUse case
--softMovesKeptKeptRedo the commit while retaining staged changes
--mixed (default)MovesResetKeptUncommit but keep edits unstaged
--hardMovesResetResetDestructive: discards tracked working-tree changes

Do not run git reset --hard as a generic cleanup command. It discards tracked unstaged and staged changes. It does not remove untracked files. Never reset shared history without coordinating.

Module 7 · Recover a moved reference [Dev]

The reflog records where local references pointed.

Find a prior position

git reflog
git show HEAD@{1}

Reflog entries help locate recently moved branch tips and commits that are no longer easy to reach.

Recover without rushing

Inspect the candidate commit. Create a rescue branch before doing more work:

git branch rescue/recovered HEAD@{1}

Reflogs are local and expire over time; they cannot restore uncommitted edits that were discarded.

Decision guide: shared commit to undo → revert; local commit to reshape → consider reset or amend; lost branch tip → inspect reflog; uncommitted file edit → inspect diff before restore.

Recovery works best when you stop, inspect, and make a rescue referenceModule 7

Module 8 · Protect what you share [Dev] [Architect]

Prevention is simpler than cleaning a published history.

Never commit secrets

Store credentials in approved secret managers. If exposed, revoke or rotate immediately—even if the commit is later removed.

Enable platform secret scanning and review access to affected systems.

Handle large files deliberately

Git stores snapshots; frequent changes to large binaries can grow repository history. Git LFS keeps pointers in Git and file content in separate storage.

Check quotas, retention, access, and backup policies before adopting LFS.

Secure the path

Least-privilege access, protected branches, required review, and signed commits/tags can strengthen provenance.

Anti-patterns to avoid

Giant unrelated commits, force-pushing shared branches, long-lived unintegrated branches, committing generated output blindly.

Deleting a secret file in a later commit does not erase earlier copies from history or clones. Rotate first; then follow your incident and repository-cleanup process.

  3. Inspect the graph with git log --oneline --graph --all.
  4. Try git reflog to see local branch movements.

This exercise changes only files in git-practice. Never experiment with reset, restore, or conflict commands in a repository containing work you care about.

Reference · FAQ & further reading [All]

Common questions, short answers.

Is Git a backup?

Not by itself. A local repository is one copy; use an approved backup and hosting strategy for important work.

Does every commit go to GitHub?

No. Commits are local until pushed to a remote. You can make and inspect local commits offline.

Should we always rebase?

No. Follow the team convention. Rebase can create a linear history but rewrites commit IDs; avoid rewriting shared history.

Why does a merge conflict happen?

Git cannot determine the intended result of overlapping edits or incompatible file operations. A human must resolve and verify the combined change.

Can I recover a deleted branch?

Often, if its commit is still reachable in the local reflog. Inspect first, then make a rescue branch. Reflogs expire and are local.
